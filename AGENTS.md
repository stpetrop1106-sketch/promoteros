# PromoterOS

Operating system for promotion / experiential-marketing / field-staffing agencies.
Coordinators stop chasing promoters by phone and WhatsApp; the system proposes who fits,
sends the invitation, handles the accept/decline, refills a cancelled shift, tracks arrival,
and collects field data for the client report.

**Primary market:** Greek promotion agencies. **The UI is bilingual (el/en) from the first screen.**
**Primary user:** the coordinator. Every feature is judged by whether it removes work from their day.

The domain language is promotion-specific on purpose — `promoter`, `campaign`, `brief`, `shift`.
Do not abstract it into `worker` / `job` "for later verticals". Concrete names make the product legible
to the buyer; renaming later is one migration.

## Non-negotiable constraints

These are not style preferences. Violating them breaks the product legally or commercially.

1. **Never use real data from any existing agency.** No exported CSVs, no real promoter names or
   phone numbers, no real client names, no copied report templates. All seed and demo data is
   synthetic and generated by `scripts/seed.ts`. If you are asked to import a real file, stop and say so.
2. **Consent is not our legal basis for promoter data.** The employer/worker power imbalance makes it
   invalid (Greek DPA has fined on exactly this). Use contract necessity + documented legitimate interest.
   Do not build a consent-checkbox gate as the compliance story.
3. **Check-in geolocation is one-shot, foreground only.** Capture position at the moment the promoter
   taps "check in". Never `watchPosition`, never background tracking, never store a trail.
   Persist only `distance_from_store_m` and `within_geofence`. Always give a manual override path —
   location must never be the sole gate on someone getting paid.
4. **No cross-tenant data leakage, ever.** Agencies in this market compete for the same clients and the
   same promoters. No shared talent pool, no cross-tenant benchmarks, no "industry averages".
   Tenant isolation is a feature we sell, not an implementation detail.
5. **Messaging channel is always behind an adapter.** Never call a messaging provider SDK directly from
   feature code. See "Messaging" below.

- **Tailwind** for styling. No component library until we have a reason
- **Vercel** for hosting
- **Anthropic API** for the narrow AI features only (see below)

Rationale is in `docs/decisions.md`. Do not swap any of this without adding a decision entry.

## The server/client boundary — read this before writing an action

Five separate parcels shipped the same bug, so it is a rule rather than a tip.

**A `"use server"` module may export ONLY async functions.** A `const`, a sync function, a class, a
re-export block — each is either rejected at build time or, worse, silently replaced by `undefined`
on the client. That second failure took down the public landing page: `initialWaitlistState` was
exported from `app/actions.ts`, `useActionState` received `undefined`, and every render threw.

**A `server-only` module must never be imported by a client component for a *value*.** A type-only
import is erased and safe; importing a constant drags the whole server module into the client bundle
and fails the production build.

So:

- State types and their `*_IDLE` constants live in a sibling `state.ts`, never in `actions.ts`.
  See `app/waitlist-state.ts`, `app/settings/team/state.ts`.
- Values shared with the browser live outside the `server-only` module.
  See `lib/team-shared.ts`, `lib/admin/plans.ts`.
- **Re-exporting does not help.** A re-export is still an export.

**`npm run dev` does not catch any of this. Run `npm run build` before claiming a parcel is done.**

## Conventions

- `snake_case` in the database, `camelCase` in TypeScript, mapping at the data-access boundary
- All money in integer cents, all distances in metres, all timestamps `timestamptz` in UTC
- Every tenant-scoped table has `agency_id uuid not null` and an RLS policy — no exceptions
- Server actions in `app/**/actions.ts`, pure domain logic in `lib/` and unit-tested
- **No user-facing string is ever inline in a component.** Every one goes through `t()` with a key,
  and both `lib/i18n/el.ts` and `lib/i18n/en.ts` are updated in the same edit. Greek is the reference
  locale — write it first, then English. A missing key must fail loudly in development, not fall back silently

## Matching

**The matching engine is a weighted scoring function, not an LLM.** The coordinator must see *why*
someone ranked third and must be able to override it. An LLM here costs explainability and buys nothing.

Hard filters first (availability, agency blocklist, client blocklist), then score:

```
score = distance_decay(km, has_transport)
      + brand_experience(client_id)
      + category_experience(campaign_type)
      + skill_overlap
      + brief_completed
      + reliability(prior_accepts, prior_no_shows)
      − penalties(recent_no_show, recent_decline)
```

Weights live in a `scoring_weights` table, tunable per agency without a deploy.
`match()` always returns **per-factor sub-scores**, never just a total — the UI renders the breakdown.

## Where AI is actually used

Three narrow places. Nowhere else.

1. **Natural language → structured filter.** "Ποιες έχουν αυτοκίνητο και είναι διαθέσιμες Σάββατο στη
   Γλυφάδα;" → a validated JSON filter object, executed as SQL. Use structured outputs so it is
   guaranteed parseable. Model: `claude-haiku-4-5`.
2. **Field report summarisation.** 40 field reports + photos → a client-facing narrative.
   Model: `claude-sonnet-5`.
3. **Draft copy for message templates** — authoring step, done once by a human, not per message.

## Messaging

WhatsApp Business API needs Meta business verification and template approval: **3–10 business days**,
outside our control. Nothing may depend on it being available.

So: an invitation is always a **signed, single-use, expiring token URL** (`/i/[token]`) that opens a
no-login page with the shift details and Accept / Decline. The *transport* for that URL is a pluggable
adapter implementing `sendInvitation(promoter, url)`:

- `ClipboardAdapter` — renders the message for the coordinator to paste. Works today, matches what
  agencies already do manually. This is the default.
- `TelegramAdapter` — zero-friction real channel for testing the loop end to end
- `WhatsAppAdapter` — becomes the default once verification clears
- `ViberAdapter` — later; Greece carries a €150/month minimum commitment

Never call a provider SDK from feature code. Add adapters, not conditionals.

## Scope discipline

**Working in this repo? Read `docs/build-plan.md` first.** It assigns file ownership per lane, freezes
the interfaces between parcels, and says what "done" means. Multiple agents work here in parallel;
editing a file you do not own destroys someone else's in-flight work.

The full vision is 60–120 developer-days. We are building in the shortest possible time, which means
saying no constantly. Build order is in `docs/roadmap.md` and it is not a menu — finish a layer before
starting the next.

**Deliberately out of scope until stated otherwise:** payroll, invoicing, a native mobile app,
route optimisation for supervisors, cross-agency marketplace, push notifications,
promoter self-service availability calendar UX.

When a feature is requested that is not in the current layer, say which layer it belongs to and
keep going.
