## Done
- **Task 1 (G7).** `scripts/verify-isolation.ts` creates two fresh synthetic agencies (Alpha,
  Beta) through the real self-serve signup path (`create_agency_for_user`, called from a real
  RLS-scoped session obtained via `auth.admin.generateLink` + `verifyOtp`, the same mechanism
  `app/login/callback/route.ts` uses), populates one full fixture row per agency in
  `promoters`, `campaigns`, `shifts`, `invitations`, `assignments`, `check_ins` and
  `field_reports`, and — using each agency owner's own authenticated session — asserts, per
  table and in both directions, that the row is visible to its own agency and invisible to the
  other. It also invites and accepts an ordinary (non-owner) team member into Agency Alpha and
  attempts the two escalations `0011_accounts.sql` was written to close: self-promoting
  `app_users.role` to `owner` via a direct PostgREST update, and inserting a `promoters` row
  into another agency via a direct PostgREST insert.
  **Result: ran against the live database — 30/30 assertions passed.** Every "cannot see"
  assertion has a paired "can see its own row" assertion with the identical query shape, so a
  broken query, a revoked grant, or an empty table would have shown up as a failure rather than
  a silent false pass — see the script's own comments for why this matters (build-plan §11
  explicitly warns against an assertion that cannot fail). Both privilege-escalation attempts
  were rejected at the database (`permission denied for table app_users`, and `new row violates
  row-level security policy for table "promoters"`), and each rejection was independently
  re-verified by reading the row back with the service-role client rather than trusting the
  error object alone. The script cleans up everything it created in a `finally` block; verified
  directly afterwards (a throwaway query against `agencies`, `promoters`, and
  `auth.admin.listUsers`) that no `ISO-TEST-*` or `iso-test-*` rows remain. Run it with
  `npx tsx --env-file=.env scripts/verify-isolation.ts`.
- **Task 2 (brief rendering).** `components/ui/Markdown.tsx` is a dependency-free renderer

## Requests to other lanes
- None required to ship this parcel. One thing worth knowing for whoever next touches
  `vitest.config.ts` (P15/lane A): this was the first test to import a `.tsx` component, and it
  exposed that Vitest's esbuild transform inherits the root `tsconfig.json`'s `"jsx": "preserve"`
  (needed for Next's own SWC/Babel pipeline) and fails to strip JSX for `.tsx` files under
  Vitest as a result ("make sure to not set jsx to preserve"). I did not touch
  `vitest.config.ts` — out of this parcel's scope — and worked around it by writing
  `Markdown.tsx` with `createElement` calls instead of JSX syntax (identical behavior, JSX
  compiles to exactly this). If a future component test wants to write actual JSX, `vitest.config.ts`
  will need an explicit `esbuild: { jsx: "automatic" }` (or equivalent) override.
