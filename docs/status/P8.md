  `docs/status/P9.md`, the schema (`0001_init.sql`, `0002_rls.sql`), and the matching SQL
  (`0003`/`0005`/`0007`) to confirm `match_promoters` already excludes anyone with a *confirmed*
  assignment or a pending/accepted/declined invitation for the shift, and does **not** exclude a
  promoter whose assignment was cancelled — so cancelling makes that promoter (and everyone else)
  immediately eligible again with no SQL change needed, and P8's "surface replacements
  immediately" requirement needed no `lib/matching` change.
- **Coverage indicator** — a `Badge` in the page header, "{filled} of {required} filled",
  `ok`/`warn` by whether it's met.
- **P8 — replacement panel.** Shown whenever `confirmedCount < promoters_required`. A "why"
  box lists who declined (with when + reason) and who was cancelled (with when + reason), plus a
  pending-invitations count — shown only when there is history to explain, never on a shift that
  was simply never touched yet. Below it, the next 3 candidates from `matchPromoters(shiftId, 3)`
  with their score breakdown (`ScoreBar` + `topReasons`) and the **existing, unmodified**
  `InviteButton`/`invite` action — re-inviting is not a second code path. Cancelling a confirmed
  assignment is done from the status board (see below), calls `refreshShiftStatus`, and — because
  `match_promoters` never excluded a cancelled assignment's promoter — the freed slot and a fresh
  candidate list are both visible on the very next render (the page is `force-dynamic`, so no
  manual revalidation is even needed for this to be live).
- **P10 — status board.** One table, one row per participant (by promoter, not by invitation —
  an accepted invitation and its assignment are the same person, shown once). Every row carries a
  `tier` (0..3) that drives both the sort order and the badge colour: **0/red** = "awaiting reply"
  with the shift starting within 60 minutes or already started, a confirmed-but-not-checked-in
  row after the shift has started, or a marked no-show; **1/amber** = expired-no-answer, declined,
  or checked in via manual override (shown honestly, never conflated with a GPS confirmation, per
  CLAUDE.md §2 item 3); **2** = a healthy confirmed/awaiting-reply/checked-in-via-GPS row;
  **3** = a cancelled assignment, kept for the record at the bottom rather than deleted. Exceptions
  sort first by construction, not by a UI filter someone could turn off.
  Cancel and mark-no-show are separate confirm-gated `Button variant="danger"` client components,
  never adjacent to a common action (commercial-architecture.md §6) — they only render on rows
  where they apply (a confirmed assignment; no-show additionally requires the shift to have
  started).
- **Athens time, done right.** `app/shifts/[id]/time.ts`: `on_date`/`start_time` are naive local
  values with no zone of their own, so "is this shift starting soon" cannot use
  `new Date(dateString)` (parses as UTC midnight — exactly what CLAUDE.md warns against). Instead
  both the shift's wall-clock instant and "now in Athens" (via `Intl.DateTimeFormat` with
  `timeZone: 'Europe/Athens'`) are expressed in the same "local time treated as if UTC"
  convention via `Date.UTC`, so they are safe to subtract even though neither is a true UTC
  instant. A separate `formatAthens` handles real `timestamptz` values (`sent_at`,
  `checked_in_at`, …), which need no trick — `Intl.DateTimeFormat` with an explicit zone is
  correct for those directly.
- **Security.** `cancelAssignment` and `markNoShow` never touch the admin client at all: both ids
  are re-read through the RLS-scoped client first (`assignments` select by id, agency enforced by
  `0002_rls.sql`'s `tenant_isolation` policy), the row's current status is checked
  server-side before any write (`not_confirmed` if already cancelled/no-show/completed — a form
  double-submit or a stale page cannot cancel twice), and the `shiftId` in the form is cross-
  checked against the assignment's own `shift_id`. Same shape `invite` already used for its ids,
  just without needing the admin-client compensation `invite` has, because these two actions
  never call into `lib/invitations.ts`'s admin-client functions at all — only `refreshShiftStatus`,
  which is safe to call with a shift id that RLS has already proven belongs to this agency.
- **Bug caught and fixed before it shipped:** the first version of `board.ts` marked a promoter
  "seen" (and hid their invitation row) the moment they had *any* assignment row, including a
  cancelled one. Since a cancelled assignment doesn't exclude that promoter from
  `match_promoters`, re-inviting the very person just cancelled is a real path — and the bug would
  have silently hidden their new "awaiting reply" row behind the old "cancelled" one. Fixed:
  only a non-cancelled assignment marks a promoter "seen"; a cancelled one still renders its own
  row but no longer blocks a fresh invitation from also showing.
- **Quality bar.** One primary action per screen section (invite in the replacement panel, cancel
  *or* no-show per board row, never both offered as equally weighted). Empty states teach
  (`shifts.board.none_title/description` tells the coordinator what to do next, not just that
  there's nothing). All new strings are `t()` keys, Greek written first, both dictionaries
  updated in the same edits. Errors from the two new actions are mapped through a small known-
  reason allowlist to a specific Greek sentence — never the raw `"not_found"`/`"save_failed"`
  code, never "something went wrong". Server components throughout; `"use client"` only on the
  two confirm-gated buttons, which need `useActionState`/`window.confirm`.
- **`npx tsc --noEmit` — zero errors, whole project**, verified after every meaningful change,
  not just at the end.
