## A regression I introduced and then caught — worth one review

Fixing A3-01 broke something the old bug had been accidentally protecting. Before, a transport
failure produced **no state at all**, so React never reset the form and the promoter's typed values
survived (the audit noted this as "the one good part"). The moment a rejection became a state,
React reset the uncontrolled form — and my first version of the offline message appeared on a form
that had just been **wiped**, which for a field report after an eight-hour shift is arguably worse
than the silent failure.

I only found it because I stopped the dev server for real and read the input values afterwards.
The fix: `ReportActionState`'s `error` and `offline` members carry the submitted values back, and
every text field takes them as `defaultValue` — which is exactly what React restores the form to
when it resets. Re-verified with the server stopped: the alert appears **and** `unitsPromoted` is
still "42" and the notes are still there. If anyone reviews one thing in this parcel, make it
`readReportValues` and the `defaultValue`s in `app/c/[token]/report/report-form.tsx`.

**Diagnosis.** `app/a/[token]/data.ts:75-77` gates on `status === "archived" || "blocklisted"` and
returns `inactive`; its own comment calls that "the closest thing we have to revocation". No other

archiving stops the availability page and leaves the invitation page, the arrival page and the
field report working, including the accept button.

**The exact change I would make.** Gate the *writes* and the accept button, not the report:

1. `lib/invitations.ts:loadInvitation` — add `promoters(full_name, status)` to the select (the
   embed is already there for the name), carry `promoterActive: status !== "archived" && status

   `promoter_availability.error.inactive` sentence instead of `<RespondForm>` when it is false.
2. `lib/invitations.ts:respondToInvitation` — after the invitation row is read, one extra

3. `lib/checkins.ts:submitCheckin` — the assignment select already reaches `shifts`; add a

4. **Deliberately NOT gated:** `submitFieldReport` and `attachReportPhoto`. Someone who has already

## Decisions for the owner, not code

### A3-19 — availability cannot express a window that crosses midnight
`START_TIMES` runs 06:00–22:00, `END_TIMES` 08:00–23:00, and `planRow` rejects `toTime <=
fromTime`. A promoter available 22:00–02:00 cannot say so. The matching filter
(`from_time <= shift.start_time and to_time >= shift.end_time`, `0007_match_radius.sql`) has the
same limitation, so the gap is at least consistent across the engine — which is why the audit
flagged it as a design question rather than a defect, and why I have not invented an answer.
Promotion work does run past midnight. **Ask:** either widen the model, or write "night shifts are
out of scope" into `docs/roadmap.md` so the next person does not rediscover it. `docs/roadmap.md`
is not mine to edit.

### A3-23 — full promoter tokens in the request log line
The URL scheme puts the token in the path (`lib/tokens.ts:linkFor`), so every access log line
carries it, and the payload is base64url rather than encrypted — the promoter's uuid and the expiry
read straight out of it. An availability token lives 56 days and cannot be revoked except by
archiving the promoter, so a leaked line is a long-lived credential in a place nobody treats as
secret. `docs/build-plan.md` §8 lists "no personal data in any URL or log line" as part of P16.
**The question that actually matters is not ours to answer in code:** what Vercel retains, for how
long, and who can read it. This was a dev-server observation. Flagging it for whoever owns the
production logging configuration; I made no change.
