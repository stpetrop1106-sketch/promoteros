### Migration `0013_admin.sql` (written, not applied)
- `platform_admins` (id → `auth.users`, `full_name`, `created_at`). RLS enabled + forced, **no
  policy at all**, and `authenticated`/`anon` are granted nothing on the table — there is no
  query shape, not even "select my own row," that reaches it from the browser. The only paths in
  are the `SECURITY DEFINER` functions below and the SQL editor.
- `is_platform_admin()` / `current_platform_admin_name()` — the membership check and the name
  shown in the console's own header.
- `admin_audit_log` (id, admin_id, action, agency_id, target_type, target_id, reason,
  created_at). RLS enabled + forced; policies grant `authenticated` SELECT and INSERT only, and
  — the part that actually matters — **UPDATE and DELETE are revoked from `authenticated`,
  `anon`, and `service_role`**. That last one is deliberate: the service-role client bypasses RLS
  entirely, so relying on policies alone would leave the log editable by any future code that
  reached for `lib/supabase/admin.ts`. Revoking at the grant level closes that regardless of
  which client calls it. `reason` has a `check (char_length(btrim(reason)) >= 10)` — a typed
  reason, not a checkbox.
- `agencies` gains two nullable columns: `suspended_at`, `deletion_requested_at`. **Not**
  `subscription_status` values — that column is written only by P17's Stripe webhook, and a
  suspend flag living there could be silently overwritten by the next webhook delivery. See the
  migration's own comment on why that would make suspension not actually a suspension.
- Every cross-tenant read and write is its own named function, gated by `is_platform_admin()`,
  never a generic query surface (commercial-architecture.md §5 — "no raw SQL console, ever"):
  `admin_list_agencies`, `admin_agency_summary` (both aggregates, no reason needed — "listing
  agencies... and usage counts | Always available"), `admin_view_agency_activity` (recent
  campaigns/shifts — the one read that IS a customer's operational data: writes the audit row
  first, then queries, inside the same function, so there is no window where the two could come
  apart), `admin_extend_trial`, `admin_change_plan`, `admin_suspend_agency` /
  `admin_unsuspend_agency`, `admin_mark_deletion_request` / `admin_clear_deletion_request`,
  `admin_audit_log_query`, `admin_list_platform_admins`, `admin_waitlist_stats`,
  `admin_waitlist_recent`.
- Deliberately **excluded from `admin_view_agency_activity`**: promoter names and phone numbers.
  The console never needs a promoter's personal data to answer "is this customer healthy" —
  recent campaigns and shifts (names, dates, status, store) are enough, and CLAUDE.md's
  data-minimisation instinct applies to us looking at customer data too.

  non-admin (including a real, signed-in agency owner) gets a plain 404 via `notFound()`, and
  every server action under `agencies/[id]/actions.ts` re-checks the same guard itself, because a
  server action is its own public endpoint (same reasoning `lib/team.ts` documents for why
  `0011`'s DB-level checks are the real boundary, not the UI).
- **Agencies list** (`agencies/page.tsx` + `agency-table.tsx`): name, plan, subscription status,
  trial end, counts of users/promoters/campaigns/shifts, sortable and searchable client-side (the
  full-platform dataset is small at this stage; a server-paginated table would be premature).
- **Agency detail** (`agencies/[id]/**`): aggregates (plan, status, trial, counts, suspended/
  deletion flags) are shown immediately, no reason needed. Recent campaigns and shifts sit behind
  `ActivityPanel` — a reason form that, on submit, calls `admin_view_agency_activity` (which logs
  before it queries) and only then renders the result. There is no code path that shows the
  second state without the first having already succeeded.
- **Actions** (`ActionsPanel`): read-only by default; an explicit "Enable actions for this
  agency" toggle reveals extend-trial / change-plan / suspend-or-unsuspend / mark-or-clear
  deletion-request forms, each with its own typed-reason field. Suspend's confirmation names
  consequences with counts ("This suspends {name}, {users} users and {promoters} promoters") per
  commercial-architecture.md §6, and sits behind its own reveal so it is never one click.
  Suspend/unsuspend and deletion-request are reversible flags only — nothing is deleted.
- **Audit log viewer** (`audit/page.tsx`): filterable by admin, agency and date via plain GET
  query params. No filter can hide an admin's own rows — the admin filter is "which admin"
  (default: all, self included), never "exclude me."
- **Waitlist** (`waitlist/page.tsx`): total, breakdown by promoter-count band and UTM source,
  recent signups. Read-only, no reason, no audit row — product leads, not tenant data.

## What I deliberately did not build, and why

- **Impersonation / "act as a user" support sessions.** commercial-architecture.md §5 allows
  saying no here, explicitly: "if you cannot build this safely, do not build it at all." A real
  time-boxed session needs session/cookie machinery in `lib/auth.ts` and `middleware.ts` (not
  mine), and a banner that renders on every non-admin page (`app/shifts/**`,
  `app/promoters/**`, etc. — also not mine). Building a partial version from `app/admin/**` alone
  — e.g. a flag with no real expiry enforcement, or a banner that only some pages show — would be
  exactly the "half-built impersonation feature worse than none" the brief warns against. Not
  built.
- **Suspension enforcement.** `agencies.suspended_at` is set, cleared, shown, and audited, but
  nothing currently reads it at login or on a request. See "Requests to other lanes" below —
  this needs a change in `lib/auth.ts` (`requireUser()`/`authState()`) or `middleware.ts`, both
  outside this parcel's file set. The console is honest about this: `admin.agency.enforcement_note`
  says so on the page itself, not just in this file.
- **Deletion itself.** `admin_mark_deletion_request`/`admin_clear_deletion_request` only flip a
  timestamp. The two-step, export-first erasure flow is Gate 1 work, build-plan.md §11 item G3 —
  not built here, on purpose.
- **Raw SQL console.** Not built, per commercial-architecture.md §5 — every need became a named
  function instead (see the list above).

## How the audit log is guaranteed tamper-proof

1. **RLS + grants together, not either alone.** `authenticated` gets SELECT and INSERT via
   policy (`is_platform_admin()`, and INSERT additionally requires `admin_id = auth.uid()` so an
   admin can only ever attribute a row to themselves). No UPDATE/DELETE policy exists for anyone.
2. **The grant revocation is the part that survives a bypass.** UPDATE and DELETE are revoked at
   the table-privilege level from `authenticated`, `anon`, **and `service_role`**. Since
   `service_role` has `BYPASSRLS`, policies alone would not have stopped a future bug that
   reached for `lib/supabase/admin.ts` to "fix" a row — the grant revocation does, regardless of
   which client is used.
3. **Every write goes through `_admin_write_audit`**, an internal `SECURITY DEFINER` helper
   (not granted to anyone directly) that re-derives the admin from `auth.uid()`, checks
   `platform_admins` itself, and enforces the reason length — so even a caller that skipped the
   TypeScript layer entirely still cannot write a row with a fabricated `admin_id` or an empty
   reason.
4. **`reason` has a table-level CHECK constraint** (`>= 10` characters after trimming), so even a
   hand-written `insert` in the SQL editor that skipped every function above still cannot leave a
   reason blank.
5. The only way to alter or remove a row after the fact is the table owner, by hand, in the
   Supabase SQL editor — outside the product, not a code path, and itself outside this console's
   reach to prevent (documented as a known limit, not hidden).
