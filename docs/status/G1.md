## Findings that shape the work

- `stores` (0001_init.sql:160) has `name, chain, address, lat, lng, …`. **There is no column for a
  provider-formatted address** — only the free-text `address` the coordinator types. So the
  formatted address is shown in the UI for confirmation and is *not* persisted separately.
  No migration invented.
- `stores.lat` / `stores.lng` are `double precision NOT NULL`, so a store with no coordinates is not
  even representable — "no row written if geocoding fails" is also the database's position.
- `shifts` has no break columns of any kind (checked every migration). Paid duration is
  `end_time - start_time`.
- Both shift-creation paths forbid `end_time <= start_time`: the form's zod refine
  (`campaigns.validation.time_order`) and the importer's `end_before_start` row error
  (`lib/import/row-parser.ts:119`). So an overnight shift is not representable today.
- `TranslationKey = keyof typeof el`, so a key that does not exist yet is a **type error**, not just
  a runtime one. `tsc` stays red in this lane until the requested keys land.

## What changed

### Job 1 — geocoding

- `actions.ts` gained `geocodeStoreAddress(address)`, the exact twin of
  `app/promoters/actions.ts`'s `geocodeAddress`: `requireUser()` first, `getGeocoder()`,
  `{ country: "gr" }`, null on any failure.
- `coordinates.ts` is a **new non-`"use server"` sibling** holding `parseCoordinate`,
  `isSaneCoordinate` and `readCoordinates`. It exists because a `"use server"` module may export
  only async functions, so a pure helper cannot live in `actions.ts` and still be unit-tested.
- The zod schema now **requires the address** (`campaigns.validation.address_required`) and treats
  the coordinate boxes as an optional override: blank/blank is normal, anything half-filled or
  off-globe is `campaigns.validation.coords_invalid`.
- `createShifts` geocodes **before any insert**, mirroring `app/shifts/import/commit.ts`. On failure
  it returns `campaigns.shifts_new.error.geocode_failed` and writes nothing at all — no store, no
  programme, no shifts. There is no fallback coordinate anywhere on the path.
- The form drives it with a button, `useTransition` loading state and the same `GeocodeResultBox`
  (including the low-confidence warn variant) the promoter form shows. Lat/lng stay editable: that
  is the manual override, matched to the promoter screen rather than invented.

### Job 2 — the day's pay

- `lib/shift-pay.ts`: `parseTimeToMinutes`, `shiftDurationMinutes`, `payCentsForMinutes`,
  `shiftPayCents`, `formatShiftHours`. Pure, no I/O, no status check — a function of
  `(rate, start, end)` only, so the monthly-earnings lane can reuse it and decide "was it worked?"
  itself.
- Integer arithmetic end to end: `rateCents * minutes`, then an explicit floor + remainder rather
  than a float divide, so 7,00 €/h × 7,5 h is exactly 5250 cents.
- `/i/[token]` leads with the total and keeps `{rate} ανά ώρα · {hours} ώρες` underneath it. When
  the total cannot be stated (no rate, or unparseable hours) it falls back to the old hourly row.
- `lib/invitations.ts` adds `rate_cents_override` to `createInvitation`'s select — it was selecting
  only `campaigns.rate_cents`, so the message would have quoted a different number from the page —
  and adds one pay line to the message body.

## Open questions for the owner

1. **No formatted-address column.** `stores` has one free-text `address`. The geocoder's
   `formattedAddress` is shown on the form for confirmation and then discarded; what is persisted is
   what the coordinator typed, because that column is also what the promoter reads on `/i/[token]`
   and "Ερμού 1, Αθήνα" beats Nominatim's full administrative chain for finding a door. If the
   resolved address should be kept, that is a migration and a decision, not a patch.
2. **Overnight shifts** (22:00 → 02:00) cannot be entered anywhere today: the series form refines on
   `end > start` and the importer rejects `end_before_start`. `shiftPayCents` returns `null` there
   rather than guessing a wrap, and the page falls back to the hourly rate. If overnight shifts are
   real in this market, that is a schema/validation decision.
3. **Unpaid breaks** are not modelled anywhere in the schema, so paid duration is `end − start`.
   Confirmed with the manager as a report item, not a code change.
4. **Pre-existing, not touched:** `campaigns.shifts_new.preview_count` renders "1 βάρδιες θα
   δημιουργηθούν" for a single shift. It is an i18n plural, another lane's file, and it predates
   this parcel.
