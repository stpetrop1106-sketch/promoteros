# A1 — security and data-protection audit

**Status:** in_review · **Deliverable:** `docs/audit/security.md` · No application code changed, nothing committed.

Eleven findings: **1 critical, 2 high, 4 medium, 4 low.** Each carries a reproduction that was run
against the live project, or says plainly that it is a code reading rather than an observation.

The critical one: **any staff user can make themselves the owner of their agency.** A coordinator
inserts one row into `app_user_invites` through PostgREST with the public anon key; `ensure_app_user()`
then provisions that address as `owner` on first sign-in. Reproduced end to end, including
deactivating the real owner with the legitimate `remove_team_member` RPC. `0011_accounts.sql` revoked
writes on `app_users` (P19's fix) but left `app_user_invites` with 0006's `grant … to authenticated`.
Fix is one `revoke` plus an assertion in `scripts/verify-isolation.ts`.

The two highs: an anonymous caller can drive `increment_waitlist_rate_limit` (the migration's
`revoke … from public` does not remove Supabase's default `anon` grant) and switch off the public
waitlist form for everyone; and **no code path anywhere deletes a field-report photo file**, so GDPR
erasure cannot be completed and deleting a report orphans the image permanently — both proven.

Clean and verified: 30/30 on `verify-isolation.ts`, zero rows leaked across all 35 tables probed
anonymously, admin console and its append-only audit log, cron auth, Stripe webhook, the private
photo bucket, geolocation §3, no secrets in 1,372 client-bundle files, no consent gate.

Could not reach: **no Supabase management token was provided**, so item 7 (pg_catalog: forced RLS,
`pg_policies`, `proacl`/role grants) was done black-box instead — and A1-04 proves at least one
intended REVOKE silently never applied, which is exactly what a catalog read would enumerate.
Please get the token from the owner and re-run that item. Also untested: the A1-05 read-only writes
through the UI, the waitlist flood to completion, and Supabase Auth's own OTP brute-force limits.

All probing ran inside agencies this audit created and deleted; the demo agency and ΣΤΕΛΛΑ were
never modified, and no email was sent.
