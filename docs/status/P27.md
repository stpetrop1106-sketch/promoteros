## Gate table — every team mutation, gated or not, and why

| Action | Gated? | Billing action | Reasoning |
|---|---|---|---|
| `inviteTeamMember()` | **Yes** | `"add_staff"` | Adds a seat and a cost — new operational commitment, the clearest case in this file. The seat *limit* is already enforced in the database by `invite_team_member` (`0011_accounts.sql`); this adds the general read-only block that limit doesn't cover (an agency under its seat limit but with a cancelled/grace-expired subscription could otherwise still invite). |
| `changeMemberRole()` | **Yes** | `"write"` | Neither growth nor reduction — it edits an existing member's configuration. Decided to gate it because `checkBilling`'s own type doc names "edit a campaign" as the canonical `"write"` example, and a role change is exactly that shape: no seat is added or freed, no promoter is affected, and nothing about it is a time-pressured correction forced by someone else's action (contrast with `cancelAssignment`/`markNoShow` in P24's table, which record facts about something that already happened). It's the agency's own administrative decision, made at its own pace, so there's no harm-to-data-integrity argument for leaving it open the way there is for `removeMember`. |
| `removeMember()` | **No — deliberate** | — | Removing a member *frees* a seat; it doesn't consume anything. Blocking it would trap a read-only agency (cancelled subscription, or past its 14-day grace) with staff it cannot remove — including, concretely, someone who has left the company and should lose access to the account *immediately*, not once the invoice is paid. That's worse than the billing problem it would be "protecting": an access-control gap on a read-only agency, over a feature that only reduces usage. Matches P24's `cancelAssignment`/`removeMember`-shaped reasoning: this corrects the agency's own roster, it doesn't grow what the agency is using. |
| `revokeInvitation()` | **No — deliberate, same shape as `removeMember`** | — | Revoking a pending invitation frees a reserved seat (P24's own `TeamSnapshot.seatsUsed` counts live invitations toward the seat count) and corrects the agency's own outstanding-invite list — an invite that's no longer wanted, sent to the wrong address, or for someone who changed their mind. Nothing about it is new commitment. Blocking it would leave a read-only agency stuck holding a seat reservation it cannot release, which actively works against giving it room to invite the *right* person once it does pay. |
| `loadTeamSnapshot()` | **No — read** | — | Reads are always allowed; unconditional per `checkBilling`. |
| `ownerContext()` | **No — auth/authorization, not billing** | — | Establishes who is asking and whether they're an owner. Independent of subscription state by design — a demoted or signed-out actor should get `not_owner`, not a billing message, regardless of the agency's billing status. Called before the billing check in both gated actions for exactly this reason: authorization failures should never be masked by a billing sentence. |

## Notes for the manager

1. **Order of checks in both gated actions is `ownerContext()` first, then
   `checkTeamWriteAllowed()`.** P24's note suggested calling the billing check "before
   `ownerContext()`", but `checkTeamWriteAllowed` needs `agencyId`, and the only way to get that
   without doing the owner check is a second, separate query — `ownerContext()` already does both
   in one round trip. More importantly, checking authorization first means a non-owner always gets
   `not_owner`, never a billing sentence about an account they can't administer anyway. This
   matches the established pattern in `app/promoters/actions.ts::createPromoter` (auth via
   `requireUser()`, *then* `checkPromoterCreationAllowed()`), just with `ownerContext()` standing
   in for both the auth and the role check. Flagging in case the intended reading was literal.
2. **`changeMemberRole` gated, unlike `removeMember`/`revokeInvitation`.** The brief asked this to
   be a real decision rather than a reflex; reasoning is in the gate table above. If that reading
   is wrong and role changes should stay open the same way removal does, it's a two-line revert
   (drop the `checkTeamWriteAllowed` call and the now-unused import stays used by
   `inviteTeamMember` regardless).
3. No new `TeamErrorCode` was added and no i18n keys were appended — both blocked messages reuse
   the two `enforcement.team.*` keys P24 already wrote.
