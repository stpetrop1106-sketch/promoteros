## Notes for the manager
- Blocking (cannot send): promoter status archived or blocklisted (or an agency/client `blocklist`
  row) · already confirmed on this shift · holds an unexpired pending invitation for this shift ·
  confirmed on another shift overlapping in time (half-open, same semantics as `match_promoters`'s
  own `OVERLAPS` filter — back-to-back is not overlapping).
- Warnings (can send anyway): no `available` row covers the shift's date/hours · a declared
  `unavailable` window overlaps the shift's actual hours (a window that never touches the shift is
  not a warning) · promoter outside the agency's travel radius (`scoring_weights` factor
  `distance`, `params.max_distance_km`, default 60 km — there is no per-campaign radius in the
  schema, so this reads the same ceiling `0007_match_radius.sql` uses) · campaign has a published
  brief the promoter has not acknowledged (no warning if the campaign never published one, or if
  the promoter has no geocode for the distance warning).
- Server re-check: `sendInviteFromProfile` (`app/promoters/[id]/invite/actions.ts`) calls
  `loadEligibilityForShift`, which re-reads the database from scratch (not the panel's stale
  view) and also rejects if the shift is no longer `open`/`partially_filled` (`shift_unavailable`)
  — covers the race where the shift fills or a second invitation lands between loading the panel
  and pressing send.
- Check-in link: promoter finds it on `/i/[token]` once `status === "accepted"`, both on first
  accept and every reopen (minting is stateless, like `AvailabilityLink`, so this is safe to
  recompute per view). Coordinator mints it on demand per confirmed row on `/shifts/[id]`.
- TTL: `checkinLinkTtlHours(onDate, endTime)` in `lib/checkins.ts` computes hours-until
  (shift end + 12h tail), floored at `DEFAULT_TTL_HOURS` (72h) — covers a link minted weeks ahead
  at invitation-accept time, never shorter than a coordinator-minted link already got.
  `createCheckinLink`'s own signature and default are untouched, per the P39 constraint.
- `blocking`/`warning` reason codes are more granular than the brief's four/four bullets (e.g.
  "archived" and "blocklisted" are separate) so the stated reason is specific, not a merged guess.
