## Enforcement decision — why middleware does *not* gate billing

`checkBilling()`'s own contract is "reading is never blocked." Every path in the middleware
matcher (`/shifts`, `/promoters`, `/campaigns`, `/settings`) is reached by both a page-load GET
(always a read) and server-action POSTs to that same URL — including read-only actions, e.g.
`geocodeAddress` in `app/promoters/actions.ts`. A blanket "block every POST when read-only" in
middleware would also block those reads, which is exactly the lockout this parcel exists to
prevent — middleware cannot see the read/write distinction that only the action body knows. So:

- **Suspension** (full lockout, our own deliberate act) is enforced at the one true choke point,
  `requireUser()`, with `middleware.ts` only handling the *explanation* for the one URL it
  redirects to.
- **Billing** (read-only, never a full lockout) is enforced per-action, via `checkBilling()`,
  wired here for the one write action I own (`createPromoter`). The pattern (`getEntitlement` +
  `checkBilling`, called first, distinct message per block reason) is the thing to copy — not a
  shared helper, since `getEntitlement`/`checkBilling` already are that helper.

## Notes for the manager

**Two decisions worth confirming.**

1. **Suspension is a full, unconditional lockout — no read-only carve-out.** Billing's read-only
   state still lets a customer see and export their own data because non-payment isn't their
   fault and we "never delete a customer's data for non-payment." Suspension is different: it's
   *our* deliberate act (via the admin console), and the brief's own phrasing — "a suspended
   agency writes nothing," "not a silent empty dashboard" — reads as "don't show a
   half-working product," not "show a read-only one." I implemented it as a full block (the
   explanation page, nothing else) rather than reusing the `read_only` access level. If the
   intent was actually "suspended = read-only, same as canceled," that's a one-line change in
   `lib/auth.ts` (return the user with a forced read-only flag instead of blocking) plus dropping
   the standalone middleware page in favour of the existing billing-banner pattern — flagging the
   reading I took rather than assuming it's obviously right.
2. **The suspended-user sign-out is a hand-built `@supabase/ssr` client inside `middleware.ts`,
   not a reuse of `app/login/actions.ts`'s `signOut`.** That function is a React Server Action,
   which needs the real page's encoded action reference — a static HTML form from middleware
   cannot invoke it. The duplication is ~15 lines and mirrors `lib/supabase/middleware.ts`'s own
   cookie-handling pattern exactly (read from the request, write onto the response); it was that
   or leave a suspended user with no way to sign out at all, which fails commercial-
   architecture.md §6's "no dead ends" rule.
