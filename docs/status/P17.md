## Notes for the manager

the product is unaffected.

**Keys needed** (`docs/keys-needed.md` §2 is accurate; `docs/billing-setup.md` is the how):
`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and six price ids
(`STRIPE_PRICE_{STARTER,AGENCY,MULTI_BRAND}_{MONTHLY,ANNUAL}`). All obtainable in **test mode with
no business verification**. A missing price id disables that tier's button with a sentence — it is
not an error state.

**How idempotency works.** The handler inserts the event into `billing_events` keyed by Stripe's
own `evt_…` id under a unique index, *before* acting. A retry — Stripe retries until it gets a 2xx,
and retries can outlive a success — hits `23505` and returns 200 having changed nothing. The
guarantee lives in Postgres, not in a flag application code has to remember to check. This matters
most for `customer.subscription.deleted`: replayed against an agency that has since re-subscribed,
it would cancel a paying customer.

**How signature verification works.** `verifyStripeSignature()` HMAC-SHA256s `"<t>.<raw body>"`
with the `whsec_` secret, compares in constant time with `timingSafeEqual`, accepts any of the
`v1` values (so a secret rotation does not drop events), and rejects a timestamp more than 300s
from now in *either* direction. It runs on the raw request text before anything parses it —
`JSON.parse`/`stringify` does not round-trip byte for byte, so verifying after parsing would fail
or, worse, be made to pass. Failure is a 400 (Stripe does not retry something that will never
become verifiable); a missing secret is a 503 (it stays in the retry queue).

**Two decisions I took that you should confirm.**
1. **`past_due_since` is a new column, beyond the four the brief listed.** The 14-day grace window
   needs a start, and nothing in `0011` provides one that does not move for unrelated reasons. Had
   I derived it from `current_period_end`, every dunning retry would silently restart the window.
2. **An expired trial gets the same 14-day grace as a failed card**, then read-only. §3 specifies
   dunning for `past_due` and is silent on an unconverted trial; treating it more harshly would
   lock someone out the morning after, which is exactly what the gentle-dunning rule exists to
   prevent. One line in `evaluateAccess()` if you want it stricter.

**What I could not verify without keys.** Every path that talks to Stripe: Checkout session
creation, the Billing Portal redirect, the customer create, and a real signed webhook moving an
agency row. The pure logic around them is exercised (see Done) and the failure modes all return a
specific, translated sentence rather than a crash. Following `docs/billing-setup.md` §6 with
`stripe listen` is the first real test.
