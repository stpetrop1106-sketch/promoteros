## How to create the first coordinator account

Five steps, all by hand. Nothing here is automated on purpose — creating a tenant identity is not
something the sign-in form is allowed to do (see the note on invite-gating below).

1. **Apply the migration.** Open the Supabase SQL editor and paste
   `supabase/migrations/0006_auth.sql` in full. I cannot run DDL through the JS client, so
   **this is not applied** — treat everything below as blocked until it is.
2. **Make sure the seed has run**, so the agency with slug `demo-agency` exists
   (`npm run seed`).
3. **Authorise the address**, in the SQL editor:
   ```sql
   select grant_agency_access('stella@example.com', 'Stella P.');
   ```
   (signature: `grant_agency_access(email, full_name, slug default 'demo-agency', role default 'coordinator')`)
   That writes an `app_user_invites` row, and if the person has already signed in once it attaches
   them immediately. Verify with `select * from app_user_invites;`.
4. **Set the auth redirect allowlist** in the Supabase dashboard → Authentication → URL
   Configuration. Site URL and Redirect URLs must include
   `http://localhost:3000/login/callback` and `https://<vercel-preview>/login/callback`.
   A link that redirects anywhere else is rejected by Supabase and lands on
   `/login?reason=link_failed`. `NEXT_PUBLIC_APP_URL` in `.env` must match the origin being used.
5. **Sign in.** Visit `/login`, enter the address, open the emailed link **on the same device and
   browser** that requested it — PKCE stores the verifier in a cookie there.

To add a second coordinator, repeat step 3 only.

## How tenant isolation should be verified

Do not accept "the pages load" as evidence. It proves the happy path, not the boundary.

1. **Two tenants, two accounts.** In the SQL editor create a second agency and give it one shift:
   ```sql
   insert into agencies (name, slug) values ('Rival Agency', 'rival-agency');
   select grant_agency_access('rival@example.com', 'Rival Coordinator', 'rival-agency');
   ```
   Sign in as each address in two different browser profiles. `/shifts` must show each agency's own
   rows and nothing else, and the counts must not overlap.
2. **Direct id probe — the one that matters.** Copy a shift id visible to agency A and open
   `/shifts/<that id>` while signed in as agency B. It must 404. If it renders, RLS is not on.
3. **Forged server action.** POST to the invite action with agency A's `shiftId` while signed in as
   B. It must return `not_found`, not an invitation.
4. **Signed out.** With no session, `/shifts` must redirect to `/login`; `/i/[token]` must still work
   untouched.
5. **At the database, not the app** — the honest check, since it bypasses every line of TypeScript:
   ```sql
   set local role authenticated;
   set local request.jwt.claims = '{"sub":"<agency B user uuid>","role":"authenticated"}';
   select count(*) from shifts;   -- must equal agency B's shift count, not the total
   reset role;
   ```
6. **Automated.** This belongs in P15 as a permanent test, not a one-off manual pass — build-plan §8
   requires P1 to prove a second agency's rows are invisible. I do not own `tests/**`, so the test
   is not written. Recommend it as the first thing P15 adds.

## Notes for the manager

- **The migration is written, not applied.** `supabase/migrations/0006_auth.sql`. Until it runs,
  `ensure_app_user` does not exist, no `app_users` row is ever created, and `/shifts` will bounce
  every sign-in to `/login?reason=no_agency`. That failure mode is correct behaviour, not a bug.
- **Magic-link delivery is unverified.** I could not send or open a real email from here. Supabase's
  built-in sender is rate-limited (a few per hour) and frequently does not deliver at all, so
  **an SMTP or Resend key from the user is needed** before anyone relies on this. Everything around
  the email is built and does not change when the sender does: only the Supabase dashboard SMTP
  settings change. If delivery is a problem while testing, the SQL editor can mint a link directly,
  or a password can be set on the user in the Auth dashboard.
- **Decision: sign-in does not grant access.** Anyone can request a magic link and get a Supabase
  session; only a pending `app_user_invites` row turns that into an `app_users` row. Auto-attaching
  first sign-ins to `demo-agency` would have been three lines less, and would have had to be undone
  the day a second agency exists — build-plan §2.1's test says do it properly now. The cost is step 3
  above.
- **Decision: RPC, not a trigger on `auth.users`.** A trigger fires when the magic link is
  *requested*, which would provision a tenant row for an address that has not proved it can receive
  mail. `ensure_app_user()` runs only once a verified session exists. It is idempotent.
- **The login form never says whether an address is known.** Same reply either way. Distinguishing
  them would let a competing agency probe for who works where.
- **`middleware.ts` is matched narrowly** — `/shifts`, `/promoters`, `/campaigns`, `/settings`,
  `/login`. The marketing pages and the promoter token URLs are deliberately not matched, so P1 adds
  no auth round trip to a promoter tapping a link, and cannot break `/i/[token]`. P16 also wants
  `middleware.ts` for rate limiting — it will need to widen the matcher to `/i/*` and `/c/*` and add
  its logic alongside `updateSession`, not replace it.
- **`0006` also fixes a trap the swap would otherwise spring.** Everything ran on the service role
  until now, which needs no table privileges. The RLS client connects as `authenticated`, so the
  tenant tables need `GRANT`s as well as policies. A missing grant reads as a permission error and a
  missing policy as an empty list, and they are easy to confuse at 2am — the migration grants them
  explicitly rather than trusting Supabase's default privileges.
- **Not verified end to end by me:** the migration running cleanly against the live database, email
  delivery, and a real cross-tenant probe with two live accounts. Everything typechecks and the
  reasoning is above, but treat the isolation checklist as work still to do, not a summary of work
  done.
