## How privilege escalation is prevented

The important part, because the obvious implementation is wrong. **A server action is a public
HTTP endpoint — and so is PostgREST.** The browser holds the anon key and a session, so it can
skip `app/settings/team/actions.ts` entirely and write to the database directly. Before this
migration, `0006` granted `insert, update, delete` on `app_users` to `authenticated`, and the
`0002` policy allows anything inside your own agency. That combination permitted, from any
coordinator's browser console:

```
update app_users set role = 'owner' where id = <their own id>;   -- self-promotion
insert into app_users (id, agency_id, role) values (…);          -- minting a colleague
delete from app_users where id = <the owner's id>;               -- removing the owner
```

So the fix is at the table, not in the UI:

1. **`revoke insert, update, delete on app_users from authenticated`**, then
   `grant update (full_name, phone)` back. Role, agency and active are not writable by the role
   the browser holds, at all.
2. Every membership write goes through a `security definer` function that re-derives the actor
   from `auth.uid()` and calls `is_agency_owner()`. Nothing is taken from a form field.
3. `set_team_member_role` refuses `p_user_id = auth.uid()` outright — **nobody changes their own
   role**, owner included.
4. Demoting or removing the **last active owner** raises `last_owner`.
5. `accept_agency_invitation` takes **only a token hash**. The agency, the role and the permitted
   email address are read off the stored row, so a forwarded link cannot join anyone to an
   arbitrary agency, and it must be redeemed by the address it was sent to. Single-use, expiring,
   hashed at rest.
6. `current_agency_id()` now requires `active` (see below).
7. The UI's owner-only rendering is presentation, not security; the code says so where it matters.

## Two changes outside my table set — please read before applying

1. **`current_agency_id()` is replaced** (it was defined in `0002`) to add `and active`.
   Removal is recorded as `active = false`, and without this a removed coordinator kept a valid
   `current_agency_id()` and therefore kept full RLS read access to the agency they had just
   been removed from. `lib/auth.ts` refused them; PostgREST would not have. Same signature, so
   every existing policy keeps working.
2. **`app_users` grants are narrowed**, as above. If anyone re-runs `0006_auth.sql` after `0011`,
   its grant loop restores `insert, update, delete` on `app_users` and reopens the hole.
   **Re-run `0011`'s privileges block if `0006` is ever re-applied.**

**Enum ordering / how to run it.** `alter type user_role add value 'owner'` is the first
statement in the file and is marked **STEP 1 — run it on its own**, then run STEP 2. The Supabase
SQL editor wraps a pasted script in one transaction, and a new enum value cannot be *used* in the
transaction that adds it. I wrote STEP 2 so that it never names `'owner'` at DDL-parse time —
every reference is either `role::text = 'owner'` or inside a plpgsql body — so pasting the whole
file at once should also work on PG 12+. Running the two steps separately is the safe order.
The value is **appended**, so the enum sorts `coordinator < supervisor < admin < owner`. Nothing
compares roles ordinally; a screen that wants owners first must order explicitly.

## Notes for the manager

- **`admin` is not offered anywhere.** It is the legacy `0001` value and means nothing in the
  §1 role model; a second kind of privileged user would only be confusing. Existing `admin` rows
  render correctly and can be changed to a real role.
- **Removal is deactivation, never deletion** (§6): the person's name stays on the work they
  created, the seat is freed, outstanding invitations for them are dropped, and re-inviting them
  reactivates the same row with its history.
- **A new agency gets default `scoring_weights`** inside `create_agency_for_user`, copied from
  `scripts/seed.ts`. Without them `match_promoters` would fall back to per-factor defaults but
  the settings screen would have no rows to tune — and an agency whose first ranked shift looks
  arbitrary has had the aha moment wasted on it.
- **Slugs.** Greek agency names strip to nothing under `[^a-z0-9]`, so most self-serve agencies
  get `agency-<6 hex>`. The slug is an internal handle and is never shown; I did not add
  `unaccent` for this.
- **`agency_invitation_preview` is granted to `anon`.** It is keyed on the token hash and returns
  only the agency name, the invited address and the role. Someone who has just clicked the link
  in their email has no session yet and must still be told who invited them; it reveals nothing
  to anyone who does not already hold an unguessable hash preimage.
