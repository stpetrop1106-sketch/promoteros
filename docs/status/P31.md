## Notes for the manager
- No migration needed, per the brief — brief_ack, its RLS policy, and its grant already exist.
- **Where:** the acknowledgement lives on the invitation page (`/i/[token]`), not check-in.
  product-spec.md §9 says "the promoter reads it before the shift" — the invitation is the only
  touchpoint that happens with real lead time before the shift, so it's the only place an
  acknowledgement gives the coordinator a useful chase list. `/c/[token]` already showed a
  220-char truncated reminder of the brief the day of arrival, at the store; that's too late for
  the signal to be useful and left untouched (not in Files touched). Because `brief_ack` is
  keyed `(brief_id, promoter_id)`, one acknowledgement at invitation time also covers every
  later shift under the same campaign brief, which lines up with `brief_completed` already being
  a per-campaign matching factor rather than a per-shift one.
- **Idempotency:** the write is `brief_ack.upsert({brief_id, promoter_id}, {onConflict:
  "brief_id,promoter_id", ignoreDuplicates: true})`, i.e. `ON CONFLICT DO NOTHING` — a retry or a
  next-day reopen inserts nothing new. The displayed date is always read back from the row after
  the upsert, never computed locally, so a second tap can never show a moved timestamp.
  `quiz_score` is never included in the payload, so it stays null as required.
- **What's new for the coordinator:** before this parcel, "who has read the brief" had no
  answer anywhere in the product except a seed script. Now the brief screen answers exactly the
  question the brief said gets asked before every activation, with the actionable half (who
  hasn't) surfaced first.
- `lib/briefs.ts` deliberately re-verifies the invitation token and re-reads the invitation row
  itself rather than importing from `lib/invitations.ts` (not owned by this parcel) — the same
  parallel-lookup shape `lib/checkins.ts` already uses for a different token purpose.
