## Notes for the manager

**TTL: 56 days — eight weeks, four of the fortnights the page renders.** An invitation token is
24h because it concerns one shift and then it is dead. An availability link is the opposite kind of
object: the promoter keeps it in their chat history and reopens it whenever their month changes, so
an hours-long TTL would put the coordinator straight back into re-sending links, which is the work
§2 exists to remove. Eight weeks is long enough to span a season and short enough that an anonymous
credential forwarded to the wrong chat dies on its own. An expired link says "this link has expired
— ask your coordinator for a new one", never a dead page. **Caveat you should know about:** there is
no `token_hash` column for these links (that would be a migration), so a link cannot be revoked
early, only out-waited — or cut off by archiving/blocklisting the promoter, which the loader checks
on every request.

**What the page can see:** `promoters.full_name` (so the promoter knows the link is theirs),
`promoters.status` (to decide whether the link still works), `promoters.agency_id` (required by the
`availability` insert, never returned to the page or the client bundle), and that one promoter's
`availability` rows inside the 14-day window. **What it cannot see:** phone, email, birth year, home
coordinates, reliability score, rate, work history, campaigns, clients, stores, shifts, the agency's
name, or any row belonging to another promoter. There is no join out of `app/a/[token]/data.ts`
that could reach one — a promoter cannot learn from this page that another promoter exists.

**No contradictory rows:** `planRow()` maps one choice to **at most one** row, and the save action
**deletes the date's rows and then inserts that single row** — never an upsert, which keyed on
`(promoter_id, on_date, from_time)` would happily leave a whole-day `available` row sitting beside a
partial `unavailable` one (the exact case `0005_matching_fixes.sql` FIX 2 had to teach the matcher
to survive). supabase-js cannot wrap the two statements in a transaction and this parcel adds no
migration, so the failure is arranged to fall the safe way: if the insert fails after the delete the
date is left *cleared*, not contradictory, and the promoter is told the day did not save. The grid
also flags any date that already holds two rows, and the next tap collapses it to one.

**Two in-flight boundary bugs I saw and did not touch** (both were fixed by that lane within the
hour, but they are the sixth and seventh instances of the same rule): `app/settings/agency/
agency-identity-form.tsx` imported `RETENTION_MONTHS_MIN/MAX` as *values* from the `server-only`
`lib/agency-settings.ts`, which failed the production build exactly as CLAUDE.md predicts; and
`components/ui/Avatar.tsx` had two `noUncheckedIndexedAccess` errors that `npm run dev` never
surfaced. The rule is earning its place in the file.

**One decision I took that you may want to reverse:** the promoter's save is **not** behind
`checkBilling()`. A read-only agency can still receive availability a promoter declares. It writes
no commercial object, it is initiated by the promoter rather than the agency, and blocking it would
punish the promoter for the agency's invoice. Minting the link is a pure HMAC and writes nothing, so
there is nothing to gate there either. Say the word and it is three lines in
`app/a/[token]/data.ts`.
