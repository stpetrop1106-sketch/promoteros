## Done
- **A1-01 / A1-02 / A1-04 — grant lockdown.** Migration 0018 applied, then the audit's own attacks
  re-run against the live database with the public anon key, from a real coordinator session in a
  real agency the probe creates and deletes. Coordinator minting an owner: **HTTP 403 42501**, both
  by INSERT and by PATCH. Anonymous rate-limiter abuse and anonymous `admin_suspend_agency`: **401
  42501**. Denial is at the grant level, before RLS, so it does not depend on the role being read
  correctly. The paths the product needs still work in the same run: anonymous staff-invitation
  preview 200, `ensure_app_user` 200 with the coordinator really coming back as `coordinator`, and
  an owner inviting staff 200.
- **A2 finding 2 — `/privacy/promoters` 500 with a second agency.** The controller now comes from
  the promoter's own signed token (`lib/promoter-controller.ts`), so the notice is per-agency
  without a guessable parameter. **Verified with a second agency row actually in the database:**
  `/i`, `/c`, `/a` each 200 naming the right agency, unknown token 404. The unparameterised route
  resolves the signed-in owner's own agency and 404s instead of 500ing when nothing identifies a
  controller.
- **A1-03 (the real part) — orphaned photo files.** Nothing had ever deleted a stored photo; a
  campaign delete cascades in Postgres and leaves the files behind forever. The daily cron now
  reconciles the bucket against `report_photos`. **Verified against the live bucket** with a
  deliberately created orphan: scanned 3, referenced 2, deleted exactly the orphan, both real
  photos intact; and through the cron route itself (scanned 2 / referenced 2 / deleted 0).
  Retention for photos that still have rows is deliberately unchanged — see `lib/retention.ts`.
- **A1-07 / A3's confirmation — no rate limiting on promoter endpoints.** `middleware.ts` did not
  even match `/i`, `/c`, `/a`, so there was no layer a limiter could sit in. Now 60 requests per
  minute per address per route family, keyed on the address and never on the token. **Verified:**
  a 75-request burst got 60 × 200 and 15 × 429 with `Retry-After: 40` and the Greek page; a
  promoter on a different address was unaffected.

- **A1-11 — stale `waitlist_rate_limit` rows.** The table swept itself only while the form was
  being used, so with no traffic it kept whatever was in it; the audit found rows eleven days old.
  Now swept by the daily cron. **Verified against the live table:** two stale rows before,
  `waitlistRowsSwept: 2` in the cron's response, zero rows after.
- **A1-05 — write paths with no billing gate.** Eight were listed. Three now carry one
  (`updatePromoter`, `saveAutoAvailabilityLinks`, `sendAvailabilityLinksNow`) and **five
  deliberately do not**, each documented in the file itself rather than left looking forgotten:
  `cancelAssignment` and `archivePromoter` free capacity, `markNoShow` records something that
  already happened, `mintCheckinLink` serves a shift confirmed while the subscription was live,
  and `saveAgencyIdentity` writes the legal name `/privacy/promoters` refuses to render without —
  gating that would block a legal obligation to collect a subscription. This is P27's rule: a
  read-only agency is stopped from taking on anything new, never trapped.
- **A1-06 — the gate failing open on a null entitlement.** `lookupEntitlement()` now separates
  "no such agency" (refused) from "the lookup failed" (allowed, and logged — locking a paying
  customer out because Postgres hiccuped is the worse failure). `checkBillingFor()` replaces the
  `entitlement && !checkBilling(...)` idiom so the decision is made once. **Worth saying plainly:
  this was never exploitable from the UI.** The `own_agency` RLS policy is
  `id = current_agency_id()`, so a signed-in coordinator always sees their own row, and
  `requireUser()` has already redirected anyone without one. It mattered for the caller that does
  not exist yet — a cron, a webhook, an admin client.

- **Tenant isolation re-verified after everything above.** `scripts/verify-isolation.ts` against
  the live database: **30/30 assertions passed** — two fresh agencies created through the real
  signup path, a full fixture set each, then every tenant-scoped table checked in both directions
  plus both privilege escalations. Worth doing precisely because migration 0018 changed grants and
  the middleware now intercepts three route families; isolation is the one property CLAUDE.md §4
  says we sell. Both test agencies cleaned up.
- **A1-10 — raw Postgres text on the coordinator's screen.** Re-read rather than assumed, and the

## Wired but NOT driven end to end
The three new A1-05 gates and the A1-06 null handling are mechanically identical to the P24/P27
gates already in the codebase, and they typecheck — but I did not watch a read-only agency be
refused, because every one of these actions needs a signed-in owner session and the only agency in
the database is the customer's own. **Before this is handed to a customer, the read-only path
deserves one deliberate pass**: put a throwaway agency into `canceled` past its grace, sign in as
its owner, and try each gated action. That is a real gap in my verification, not a formality.

## Notes for whoever reads this next
- **Two of my own verifications were worthless before they were right, in the same way each time:
  the negative path short-circuited.** The 0018 probe first reported four tidy "BLOCKED" lines
  while holding no session at all. The limiter's first test reported "no limiting" because 75
  *sequential* requests to a dev server take longer than the limiter's own one-minute window, so it
  kept rolling over; fired as a burst it refused 15 immediately. A refusal you did not cause proves
  nothing, and neither does an allowance you gave yourself a minute to earn.
- **`next dev` rewrites `tsconfig.json`.** Every lane's dev server appends its own
  `NEXT_DIST_DIR/types/**/*.ts` to `include`, and four stale ones (`.next-A2`, `.next-A3`,
  `.next-P37a`, `.next-P42b`) had accumulated in the working tree. Each declares its own
  `type AppRoutes`, so `tsc` was rejecting `<Link href>` values for routes that genuinely exist.
  None of it was ever committed; `tsconfig.json` is back to the committed version. If typed-route
  errors appear for a route you just created, this is why.
- **`middleware.ts` is CRLF.** A multi-line string replacement written with `\n` silently matches
  nothing, and `String.replace` does not complain. Two of my edits "succeeded" without applying.
