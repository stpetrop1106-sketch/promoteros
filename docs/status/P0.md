afterwards; the numbers above must be unchanged (both fixes are no-ops against today's seed data).
It is a single `create or replace function match_promoters(...)` with the identical signature. It
changes exactly two things — I diffed it against `0003` to confirm nothing else moved:

- **Fix 1 — an un-geocoded promoter ranks FIRST with a blank score.** `promoters.home_lat/home_lng`
  are nullable. `haversine_m` → null → `distance_score` → null → the whole weighted sum → null, and
  **PostgreSQL sorts `DESC` as NULLS FIRST**, so `order by r_score desc` puts them at the top of the
  coordinator's list. Zero promoters are affected today. **P3 ships a manual geocoding override
  specifically because geocoding fails**, so this fires the first time an address does not resolve.
  Fix: distance factor coalesces to 0, and both sort keys pinned `NULLS LAST`.
- **Fix 2 — an `unavailable` window overlapping the shift is ignored.** The filter only asks whether
  an `available` row *covers* the shift. `availability`'s unique key is
  `(promoter_id, on_date, from_time)`, so one promoter can hold a whole-day `available` row *and* a
  partial `unavailable` row for the same date — which is exactly what **P5** ("available/unavailable
  per promoter per day including partial days") lets a coordinator enter for "free Saturday, but not
  2–4". Today's seed writes one row per promoter per date so nothing changes; after P5 a promoter
  gets offered a shift they explicitly blocked out.

### 2. Lane A / whoever owns `scripts/seed.ts` — two seed changes. I did not make them; the file is not mine.

- **`category_experience` scores 0.00 for all 29 candidates on all 3 shifts.** Root cause is the seed,
  not the SQL: `CLIENTS` gives each of the 4 clients a distinct `type` string, `campaign_type` is
  copied straight from it, and only 3 campaigns are created — so **every `campaign_type` value belongs
  to exactly one campaign**. The SQL needs a *different* campaign of the same type
  (`c2.id <> sh.campaign_id`), which is structurally unsatisfiable. A whole factor carrying **1.0 of
  6.7 total weight (15%) separates nobody**, and it caps the attainable score at 85%.
  *Proposed fix:* give at least two campaigns the same `campaign_type` — e.g. seed 4–6 campaigns and
  draw `campaign_type` from a short shared vocabulary (`Δειγματισμός`, `Προώθηση`, `Event`) decoupled
  from the client name. Also worth checking: as written, `category_experience` is only reachable
  through `promoter_client_history`, so it is partly a proxy for brand experience rather than an
  independent signal. That is a design question for whoever owns the scoring model.

  brief read, has a car, so 4 strong factors outweigh a distance factor of 0.05. Nothing is wrong
  with the arithmetic; `distance_score` decays but never disqualifies. `smoke.ts` now flags any top-5
  candidate beyond 60 km automatically.
  *Proposed fix (seed):* keep one agency in one city, or add a second agency for Thessaloniki. Note
  `promoter_areas` ("where they will work") is populated with **random** areas uncorrelated with the
  promoter's home, so it is currently useless as a filter — that would need fixing too.
