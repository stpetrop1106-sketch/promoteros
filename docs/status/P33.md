## Notes for the manager
- **Found a real schema gap while reading migrations, not just the one 0014 documents.**
  `0006_auth.sql` grants `authenticated` only `SELECT` on `agencies`. `0012_billing.sql` then
  *explicitly* revokes `insert, update, delete` on `agencies` from `authenticated` as a defensive
  restatement, with this exact comment: "the day an owner needs to rename their agency must grant
  UPDATE (name) — a column list — and never bare UPDATE." That day is this parcel. There is also
  no RLS `update` policy on `agencies` — only the `own_agency` `select` policy from `0002_rls.sql`.
  So `db.from("agencies").update(...)` through the RLS-scoped client will fail with a Postgres
  permission-denied error *before RLS is even evaluated*, regardless of anything this parcel does
  in application code. This is a table-privilege gap, not an RLS gap.
  I do not own migrations and will not touch them. I am building the full feature — page, owner
  gate mirroring `lib/team.ts`'s `ownerContext()`, validation, specific error codes — exactly as
  specified, so it is correct and ready the moment the grant exists. The write path surfaces a
  specific, honest error (not "something went wrong") when the database refuses the write, rather
  than crashing or pretending to save. **A follow-up migration is required for this parcel to
  actually close the gap in production**: grant `UPDATE (legal_name, privacy_contact_email,
  promoter_retention_months)` on `agencies` to `authenticated`, plus an RLS `update` policy scoped
  to `id = current_agency_id() and is_agency_owner()` (both functions already exist, from
  `0011_accounts.sql`). Flagging this now rather than after `in_review` so the manager can queue
  the migration in parallel with my build.
