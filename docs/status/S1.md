## Design

### Search

`unaccent(col) ilike …` cannot be expressed in a PostgREST filter at all — a filter is
`column.operator.value`, with no room for a function call on the column — so an expression
index would have been unreachable from this app. Two **stored generated columns** instead,
each with a trigram GIN index (btree cannot serve `%foo%`):

- `promoters.search_name`       = `translate(immutable_unaccent(lower(full_name)), 'ς', 'σ')`
- `promoters.search_name_latin` = `greek_to_latin(<that same expression>)`

`ς → σ` is load-bearing: JS `toLowerCase()` applies the Unicode final-sigma rule and Postgres
`lower()` does not (`"ΣΤΕΛΛΑΣ".toLowerCase()` = `στελλας`, `lower('ΣΤΕΛΛΑΣ')` = `στελλασ`).
Without it the two sides disagree on every Greek name ending in sigma.

`search_name_latin` is what makes `Maria` find `Μαρία`. Kept a separate column on purpose: if
the transliteration is ever wrong about a letter, plain Greek search still works.

**The one correctness risk** is the SQL and TypeScript normalisers drifting apart — a
divergence makes promoters invisible with no error anywhere. `verify-promoter-search.ts`
step 1 recomputes all 62 stored values in TypeScript and demands a byte-for-byte match.
Re-run it after any change to either side.

Also fixed while in there: `.order("full_name")` alone was an unstable pager (the roster holds
"Στέλιος Καραγιάννη" three times), so `.order("id")` is now the tiebreaker; and the phone
search now also matches on digits alone, so `697 123 4567` finds `+306971234567`.

### Import

Reuses `lib/import/workbook` (SheetJS from the vendor CDN, D18; `raw: true`; Windows-1253 CSV)
and `lib/import/text` unchanged — nothing under `app/shifts/import/**` or `lib/import/**` was
modified. The field vocabulary and row shape are promoter-specific and live in
`lib/promoters/import.ts`.

Duplicate rule is `normalizePhone` against `unique (agency_id, phone)` — the same rule
`createPromoter` uses, now shared through `lib/promoters/phone.ts` rather than copied.
**Skip only, never update** (owner's decision): `updatePromoter` resynchronises
`promoter_areas`/`promoter_skills` by delete-then-insert, so "updating" from a sheet with no
skills column would silently erase a promoter's skills, and nothing distinguishes a blank
column meaning "leave alone" from one meaning "clear".

Unknown areas are reported, never created: an `areas` row needs a non-null centroid lat/lng,
and inventing coordinates would feed a made-up point into the distance scoring that decides
who gets offered a shift.

### Import — driven end to end, 2026-10-01

A real `.xlsx` (title row, blank row, Greek headers on row 3, 7 data rows) dropped into the
wizard on `/promoters`, signed in as the demo agency's owner. What was observed:

- Header row 3 found under the title and blank rows. "Βρέθηκαν 7 γραμμές με στοιχεία."
- Six of seven columns auto-mapped (`Ονοματεπώνυμο`, `Τηλέφωνο`, `Περιοχή`, `Έτος γέννησης`,
  `Αυτοκίνητο`, `Δίπλωμα`). The seventh was headed `Στοιχεία` on purpose — no synonym matches
  it — so it came through as "— δεν χρησιμοποιείται —" and was **corrected by hand to Email**.
  The three emails are in the database afterwards, so that path is exercised, not assumed.
- Preview headline: **"4 έγκυρες · 1 υπάρχουν ήδη · 2 με σφάλμα"**, matching the file exactly.
- Row 8 `Υπάρχει ήδη — ίδιο τηλέφωνο με «ΣΤΕΛΛΑ»`; row 9 `Σφάλμα — λείπει το ονοματεπώνυμο`;
  row 10 `Σφάλμα — λείπει το τηλέφωνο`. Row 7 `Με επιφύλαξη — μη έγκυρο email … άγνωστη περιοχή`.
- Result: "Προστέθηκαν 4 promoters · 1 υπήρχαν ήδη και παραλείφθηκαν · 2 γραμμές είχαν σφάλμα".

Then verified in the database, not just on screen: all four rows carry the signed-in
`agency_id` (CLAUDE.md §4); `690 001 9902` normalised to `+306900019902`; `ΝΑΙ`/`ΟΧΙ`/`✓`/blank
read correctly; `12/05/1988` yielded 1988; the malformed email stored as null; `Γλυφάδα` and
`Κέντρο, Κηφισιά` linked, `Ραφήνα` neither linked nor invented as an `areas` row; 0021's
generated columns filled themselves for the new rows (`δοκιμαστικη αλφα` / `dokimastiki alfa`).

**The duplicate**: one row for `+306970592023`, and ΣΤΕΛΛΑ byte-for-byte unchanged — not renamed
to the file's «Κάποια Άλλη», nothing updated. Skip means skip.

All four created rows then deleted; the roster compares identical to the pre-test snapshot
(62 promoters, same field values, `promoter_areas` identical).

### Still open

- **`/promoters/import` is a 404.** The importer is a modal opened from the roster header, the
  same shape as the shift importer. If a linkable route is wanted, it needs a `page.tsx`.
- **An imported promoter gets no welcome availability link.** `createPromoter` fires
  `sendWelcomeAvailabilityLink` in an `after()`; the importer deliberately does not, because
  firing 500 emails off one click is not something to decide on a lane's own authority. Needs a
  product decision: silent, opt-in checkbox, or a follow-up action on the roster.
- Transliteration is lossy by design: "Δοκιμαστικός Γάμμα" is `dokimastikos`, so a search for
  `dokimastiki` returns the three feminine names and not the masculine one. Correct, but worth
  knowing before someone reports it as a bug.

Two things the tests caught, both now fixed in `lib/promoters/import.ts`:

- "Στήλη Β" ("column B") contains "τηλ" and was being mapped to the **phone** column by the
  0.5 substring tier. That tier now needs 5 characters, not P37b's 3.
- `normalizeKeyTokens` keeps only letters and digits, so a `✓` in the car column normalised to
  an empty string and read as "no". Tick marks are now checked against the raw cell first.
