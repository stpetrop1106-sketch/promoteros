# A3 — promoter-side audit

**Status:** in_review · **Deliverable:** `docs/audit/promoter.md` · No application code changed,
nothing committed. I edited none of `app/i/**`, `app/c/**`, `app/a/**` or `app/privacy/**`.

**23 findings: 3 blockers, 8 serious, 9 annoying, 3 cosmetic.** Every one carries steps that were
actually run, or says plainly that it is a code reading (A3-09, A3-15, and half of A3-06 / A3-21).

**Worst finding (A3-01):** a field report submitted while the connection is down fails in complete
silence — no message, no disabled button, no retry, nothing saved. Reproduced by stopping the
server and submitting: the button kept its normal label and stayed enabled, and afterwards the
report did not exist. The promoter walks away believing they filed it. Two more blockers: after the
coordinator cancels an assignment the promoter's page still reads "Ευχαριστούμε! Η βάρδια
καταχωρήθηκε" and tells them to retry the arrival link later (A3-02); and inviting from the shift
page destroys the only copy of the invitation link before anyone can paste it, so the promoter is
never contacted at all (A3-03) — `InvitationLinkButton` exists for exactly this and is imported by
nothing.

**Verified working:** the token scheme (tampered signature, tampered payload, wrong purpose,
unknown id all rejected); geolocation exactly per CLAUDE.md §3 — one-shot, denied falls to the
manual override, a position in Thessaloniki was recorded anyway and the promoter told, `check_ins`
has no coordinate columns and a unique constraint on `assignment_id`; an 11.79 MB phone photo
shrunk to 673 KB and uploaded; the check-in link present on first accept and every reopen;
`/a/[token]` throughout — it is the best-built page in the set and leaks nothing about the agency.

**Could not reach:** the 24-hour expiry path (A3-09, needs a real wait or a short TTL); an archived
promoter pressing "Αποδοχή"; the check-in action on a dead connection; `capture="environment"` on a
real handset; anything over HTTPS on a real phone, including whether a long token URL survives
WhatsApp.

## Two questions answered in the report

Both are already-known A1 findings, so the report gives them evidence rather than new numbers —
see "Evidence on two questions asked during the audit" in `docs/audit/promoter.md`.

1. **Rate limiting: none.** 40 rapid `GET /i/garbage<n>` and 25 rapid `GET /a/<valid token>` (two
   DB reads each) all returned 200 — zero 429s, no `Retry-After`, no `X-RateLimit-*`.
   `middleware.ts` matches only the coordinator routes, so no middleware runs on `/i`, `/c` or
   `/a` at all. P16 lists this as a **must** and it was not built.
2. **Report photos are never deleted from storage, by anything.** No `storage…remove/delete` call
   exists anywhere in `lib/`, `app/` or `scripts/`; the only storage call is the upload at
   `lib/checkins.ts:440`. `lib/erasure.ts` deletes `report_photos` rows and counts them but never
   touches the bucket, and `lib/retention.ts:146` says photos are "flagged for review, not
   deleted". I deleted my own two objects by hand, which is exactly the point.
