## Notes for the manager

**Two decisions worth confirming**, beyond the per-action table above:

1. **`markNoShow` is treated identically to `cancelAssignment`** even though only `cancelAssignment`
   was explicitly named as needing a deliberate (rather than reflexive) decision in the brief. I
   extended the same reasoning to it because the two are the same shape: both record something
   that already happened to an existing confirmed assignment, neither creates new commitment, and
   blocking either leaves the board saying something false. Flagging in case the intended reading
   was narrower.
2. **`setCampaignStatus` is gated for all three transitions, including `cancelled`** — deliberately
   *not* treated like `cancelAssignment`, on the theory that cancelling an entire campaign is the
   coordinator's own administrative decision (not a time-pressured correction forced by someone
   else's action) and squarely matches checkBilling's own "edit a campaign" example for `"write"`.
   If that reading is wrong and campaign cancellation should stay open the same way assignment
   cancellation does, it's a one-line change (skip the gate when `next === "cancelled"`).

**The pattern used everywhere**: `getEntitlement(agencyId)` (fail open — `null` — exactly like
`checkPromoterCreationAllowed`, matching "agency not found" being `requireUser()`'s problem, not
this check's) then `checkBilling(entitlement, action)`, checked before any parsing or query runs.
Every gated action here only ever calls `checkBilling` with `"write"` (never `"add_staff"` or
`"add_promoter"` — those verbs belong to promoters and, if wired, team seats), so every block in
this parcel is `"subscription_read_only"` and needed exactly one message each — no
`GateResult.block` branching was needed outside `lib/team.ts`'s unwired helper, which does branch
(`"seat_limit_reached"` vs `"subscription_read_only"`) for whoever ends up wiring it in.
