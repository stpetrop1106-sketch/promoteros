## Notes for the manager
- **No contradictory rows possible.** `saveCoordinatorDay` and `applyBulkAvailability` in
  `./data.ts` both DELETE the target date(s) for that promoter, then INSERT at most one row per
  date (`planRow` from `lib/availability-links.ts` guarantees ≤1; the bulk path inserts one
  whole-day `available` row per targeted date, each with `from_time: null`, so no two rows in one
  batch insert can collide on `(promoter_id, on_date, from_time)`). Never an upsert. If the insert
  fails after the delete, the date(s) are left cleared rather than contradictory or stale — same
  safe-by-construction fallback `app/a/[token]/data.ts` uses, extended to a batch.
- **`self` vs `coordinator` is always visible.** Every day row carries a `Badge` naming its
  source ("She said this herself" / "You entered this") right next to the state badge
  (available/partial/unavailable/**undeclared**), so a coordinator about to overwrite a promoter's
  own answer sees that before tapping. `undeclared` (no row at all) is a distinct neutral badge and
  its own copy ("Not declared — not offered by matching") — never rendered the same as an explicit
  `unavailable` (red/`bad` badge).
  Writes are gated with `getEntitlement` + `checkBilling(entitlement, "write")` exactly like
  `app/campaigns/[id]/brief/actions.ts`; reads/writes go through `createServerSupabase()`
  (RLS-scoped), never the admin client, and every id is re-checked against the coordinator's own
  agency before any write.
- Bulk entry ships all three cases named in the brief: "all weekdays" (Mon–Fri across both weeks),
  "this weekend" (the soonest Sat/Sun pair, not every weekend in the fortnight), and "clear the
  whole fortnight" (interpreted as clearing the entire 14-day grid shown on the page, since that
  fully retires the "fourteen taps" problem the brief describes — flagging this interpretation in
  case the manager intended something narrower by "the week").
