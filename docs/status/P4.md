## Notes for the manager
- Cut: a dedicated `[id]/edit` screen for campaign fields. Editing after creation is exposed as
  status transitions only (draft → active → completed, cancel from either) via a bound server
  action, per "prefer status change over deletion" in commercial-architecture.md §6. If a
  coordinator needs to fix a typo'd name/date/rate after creation, that's the next increment.
- Shift series builder (screen 4) is the piece I protected if time ran short — it did not, so
  all five screens are built. It supports "every weekday from X to Y, HH:MM-HH:MM, N people"
  via a weekday-checkbox range (all seven checked by default, so three arbitrary dates in one
  week need no unchecking) plus a live client-side preview of how many shifts will be created,
  built on the `expandSeriesDates` helper the predecessor already wrote in `_shared.ts`.
- `campaign_skills.required` (boolean) exists in the schema but the matching engine's
  `skill_hits` query doesn't currently distinguish required vs optional skills. The new-campaign
  form's skill checkboxes insert rows with `required` left at its schema default (`false`) — a
  richer required/nice-to-have picker would be a small follow-up if the matching engine ever
  starts using that column.
- `[id]/shifts/new` fetches stores where `client_id = campaign.client_id OR client_id is null`,
  so a coordinator sees only stores relevant to this campaign's client (plus unassigned ones)
  in the existing-store dropdown, not the whole agency's store list.
- Not verified in a real browser: signing in needs a magic-link email round trip I don't have
