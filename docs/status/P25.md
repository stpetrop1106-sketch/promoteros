## Done

**Task 1 — the banner, globally, without breaking the public pages.**

- **Where it lives, and why not a coordinator-only layout.** I considered that first, per the
  brief's prompt. It doesn't work within this parcel's file scope: a Next.js layout only wraps
  routes physically nested under it, so a layout scoped to just `/shifts`, `/campaigns`,
  `/promoters`, `/settings` would require moving those four directories under a new
  `app/(coordinator)/` route group — and all four are explicitly off-limits (another lane owns
  each). `app/layout.tsx` (the root) is therefore the only layout this parcel can reach that
  actually wraps those routes, so that's where the banner fetch lives, with the public-page
  constraints handled inside it rather than by avoiding it.
- **No entitlement lookup for a public visitor.** `authState()` — the same check
  `requireUser()`/every coordinator page already relies on — runs first and is documented in
  `lib/auth.ts` to never throw for "no session." `getEntitlement()`'s three queries (agency row,
  seats used, promoters used) only run when `state.ok` is `true`. A stranger on the landing page,
  someone at `/login`, and a promoter opening `/i/[token]` are all `state.ok === false`, so the
  entitlement call — the expensive part — never happens for any of them. I did not try to also
  dodge the single `authState()` auth check itself (e.g. by pre-sniffing for a Supabase cookie by
  name) — that would depend on `@supabase/ssr`'s internal cookie-naming convention, which is not a
  contract this file should take on, versus `authState()`'s already-documented, already-relied-on
  contract of being cheap and safe to call with no session.
- **`/i/[token]` and `/c/[token]` unaffected.** Both already render with `export const dynamic =
  "force-dynamic"` and call no auth themselves (confirmed by reading `app/i/[token]/page.tsx`), so
  the root layout's new `authState()` call doesn't change their rendering mode — they were never
  statically generated to begin with. Verified live (see below): an invalid `/i/[token]` still
  renders its plain "η πρόσκληση έχει λήξει" message, no banner, no console error.
- **Root layout stays a server component.** The one bit of client-only state this needs — hiding
  the banner on `/settings`, which already renders its own copy (P22) — lives in
  `<GlobalBillingBanner>` instead, via `usePathname()`. There is no supported way for a Server
  Component layout to read the current pathname short of a header `middleware.ts` would have to
  inject (not mine to touch), so pushing just that one hook down into a small leaf component was
  the option left.
- **Never throws with no user/agency/billing row.** `state.ok` guards the whole `getEntitlement`
  call; `getEntitlement` itself already returns `null` rather than throwing when the agency row
  doesn't exist (unchanged, read-only use of `lib/billing/subscription.ts`), and the layout only
  renders `<GlobalBillingBanner>` when it got a non-null entitlement back.

**Task 2 — onboarding and the suspended state.**

- `app/onboarding/page.tsx`: a suspended, signed-in user now sees P22's own
  `enforcement.suspended.title` / `.body`, with a sign-out button (`app/login/actions.ts`'s real
  `signOut` server action), instead of falling through to the "create your agency" form. That
  fall-through was the actual bug P22 flagged — without this branch, a suspended owner following
  an old link would be invited to start provisioning a brand-new agency.
- `app/onboarding/join/[token]/page.tsx`: same explanation, placed before the `anonymous` check.
  Without it, a suspended user whose session email matched the invited address would fall through
  every existing guard (`anonymous` — no, they have a session; `signedInEmail !== invitedEmail` —
  no, it matches; `state.ok` for "already in an agency" — no, `state.ok` is `false` for
  `suspended`) straight to the accept-invitation form, letting them attempt to join a second
  agency while the database still has no idea their first one is locked. Reused the page's
  existing `signOutAndReturn` action (same pattern as the "signed in as someone else" branch just
  below it) so choosing to pursue the second invitation under a different account stays possible —
  no dead end.
